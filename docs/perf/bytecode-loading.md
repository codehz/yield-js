# 字节码加载实验

本轮只改 `Build::validate` 的函数引用查找：以按函数 ID 建立的 `BTreeMap` 取代线性扫描，复用模块校验已收集的初始化函数 ID 集合。查找支持稀疏、乱序 ID；校验项、字节码、构建摘要与快照格式不变。不把这个改动与编译 pass 或产物编码混在一起测。

## 函数引用索引：不启用

基线是 `987268d`，实验版在该提交仅应用[索引补丁](bytecode-loading/indexed-validation.patch)。按[基线复现命令](performance-baseline.md#复现)编译未插桩的 release bench，在 Apple M2（24 GiB）、macOS 27.0.1（26A434）、Rust/Cargo 1.99.1 上运行。A 批按基线 → 索引，B 批逆序；每个二进制各在独立进程预热 2 次、采样 9 次。[原始样本](bytecode-loading/)中，10 个负载的 `build_id`、产物字节数、静态指令数及帧槽数均一致。两版都通过基准的首次执行、稳态结果及各自快照续跑检查。

| 指标 | A：基线 → 索引 | B：基线 → 索引 |
| --- | ---: | ---: |
| React 首提交：启动准备中位数 | 17.086 → 16.900 ms | 17.083 → 16.893 ms |
| React 首提交：启动准备样本范围 | 16.955–17.514 → 16.747–17.285 ms | 16.984–17.262 → 16.725–17.409 ms |
| React 更新：启动准备中位数 | 17.066 → 16.963 ms | 17.122 → 16.916 ms |
| React 更新：稳态 5 次中位数 | 10.826 → 10.821 ms | 10.847 → 10.798 ms |

React 首提交的启动准备两批都降约 1.1%，但样本范围重叠，其他阶段也有同量级波动；例如未改动的 React 解码在实验版两批都慢约 0.5–0.6%。四个挂起负载的 `restore` 未见稳定改善。现有数据不足以启用额外的校验索引；补丁仅保留用于复现，没有合入验证路径。

## 构建身份校验：JSON 与 SHA-256（历史）

基于 `cb2dc40` 增加摘要内部计时，同一平台和 release bench profile，各批独立预热 2 次、采样 9 次。原始样本：[A 批](bytecode-loading/digest-a.csv)、[B 批](bytecode-loading/digest-b.csv)。10 个负载的 `build_id`、产物大小、静态指令数及帧槽数与上轮一致。四个挂起负载的快照大小不变，基准仍校验恢复后的结果。该基线采集于 SHA-256 实现；当前代码已改用 xxh3-128 + 二进制编码，下面的数字仅作历史对照。

React 首提交，中位数（样本最小–最大），单位 ms：

| 区间 | A | B |
| --- | ---: | ---: |
| 构建身份校验 | 15.961（15.776–16.131） | 15.872（15.830–16.037） |
| 摘要输入 JSON 序列化 | 4.351（4.317–4.488） | 4.335（4.290–4.398） |
| SHA-256 | 11.544（11.425–11.797） | 11.513（11.464–11.704） |
| 产物 JSON 解码（不在身份校验内） | 15.275（15.077–15.388） | 15.183（15.130–15.522） |

逐样本计算占比，SHA-256 两批中位数均为身份校验的约 72.6%，JSON 序列化约 27.4%。身份校验的其余时间包括版本检查、缓冲区释放、摘要字符串格式化和 ID 比较。该结论只针对当前平台和构建；它把单次加载实验的优先级指向**保持摘要字节及 `build_id` 完全一致的 SHA-256 加速**，不能据此判断其他平台的哈希后端。产物解码仍是独立开销；多 VM 复用已完整校验的不可变程序对象也应单独测量。

## 构建身份校验：xxh3-128 + JSON（历史）

摘要改用非加密的 xxh3-128、但当时仍构造 JSON 文本时，用同一基准重采两批；环境同上：Apple M2（8 核、24 GiB）、macOS 27.0.1（26A434）、`aarch64-apple-darwin`、Rust/Cargo 1.99.1，release bench profile。每批独立进程预热 2 次、采样 9 次。原始样本：[A 批](bytecode-loading/xxh3-a.csv)、[B 批](bytecode-loading/xxh3-b.csv)。10 个负载的静态指令数与帧槽数不变；`build_id` 全部变为 `xxh3-128:` 格式，产物字节数统一减少 30 B（`sha256:` 加 64 位十六进制变为 `xxh3-128:` 加 32 位十六进制）；四个挂起负载的快照减少 53 B（`build_id` 30 B 加绑定指纹 23 B）。基准仍校验首次执行、稳态结果及快照续跑。

React 首提交，中位数（样本最小–最大），单位 ms：

| 区间 | SHA-256 A | SHA-256 B | xxh3-128 A | xxh3-128 B |
| --- | ---: | ---: | ---: | ---: |
| 构建身份校验 | 15.961（15.776–16.131） | 15.872（15.830–16.037） | 4.505（4.428–4.541） | 4.485（4.448–4.544） |
| 摘要输入 JSON 序列化 | 4.351（4.317–4.488） | 4.335（4.290–4.398） | 4.337（4.256–4.387） | 4.331（4.292–4.387） |
| 摘要哈希 | 11.544（11.425–11.797） | 11.513（11.464–11.704） | 0.154（0.153–0.171） | 0.156（0.153–0.160） |
| 产物 JSON 解码（不在身份校验内） | 15.275（15.077–15.388） | 15.183（15.130–15.522） | 15.395（15.070–15.504） | 15.460（15.277–15.586） |

xxh3-128 两批的哈希中位数约 0.154–0.156 ms，耗时约为 SHA-256 的 1/74；构建身份校验从 15.9 ms 降到 4.49–4.51 ms（约 3.5 倍）。哈希占身份校验的比例从约 72.6% 降到 3.4–3.5%，JSON 序列化升到约 96%，成为单次冷加载的主要剩余成本。产物解码维持 15 ms 量级，样本范围与历史批重叠。SHA-256 列取自上节历史样本，xxh3-128 列为本轮新采两批；两者同平台、同基准，但不是同一进程内的交替测量。

## 构建身份校验：xxh3-128 + 二进制摘要（JSON 产物，历史）

摘要输入不再构造 JSON 文本或临时 `Vec`，但当时产物仍是 JSON：用 bincode 1.3.3 的 fixed-int、小端配置流式写入 64 KiB 缓冲，直接更新 xxh3-128。`build_id` 再次变化；产物与快照大小和上一轮相同，因为标识字符串长度不变。10 个负载的静态指令数与帧槽数不变，两批 `build_id` 一致，基准仍校验首次执行、稳态结果及快照续跑。原始样本：[A 批](bytecode-loading/binary-a.csv)、[B 批](bytecode-loading/binary-b.csv)。

二进制行的 `startup_build_digest` 同时包含编码与哈希；JSON 行保留原有的两个独立计时。构建身份校验从 4.49–4.51 ms 降到 0.676–0.680 ms（约 6.6 倍），启动准备从 5.73 ms 降到 1.90–1.91 ms（约 3 倍）。产物解码仍是最大单项，约 15.3 ms；模块初始化约 1.57 ms。JSON 文本与临时 `Vec` 都已移除；bincode 的固定整数、小端选项和 crate 版本属于 `build_id` 契约，改动会再次使所有旧产物和快照失效。

## 产物编码：二进制 artifact

产物容器改用 `Build::to_bytes` / `Build::from_bytes`：8 字节 `YIELDBLD` magic、little-endian `BUILD_FORMAT_VERSION`、bincode fixed-int little-endian payload。`Instr` 改为 externally tagged，`JsString` 与数字按 `is_human_readable()` 在 JSON 和二进制表示间分支；二进制路径不使用 untagged/内部 tag，因此不需要 `deserialize_any`。原始样本：[A 批](bytecode-loading/artifact-a.csv)、[B 批](bytecode-loading/artifact-b.csv)。

React 首提交，中位数（样本最小–最大），单位 ms；产物大小单位为字节：

| 产物大小 | 4,140,678 | 4,140,678 | 802,607 | 802,607 |
| 产物编码 | 4.343（4.284–4.404） | 4.336（4.292–4.363） | 0.547（0.524–0.555） | 0.559（0.527–0.580） |

产物缩小约 **80.6%**；解码从约 15.3 ms 降到 **0.75–0.76 ms（约 20 倍）**，编码从约 4.34 ms 降到 **0.55–0.56 ms（约 8 倍）**，React 首提交从“解码 + 启动准备 + 初始化”合计约 18.8 ms 降到约 **4.1 ms（约 4.6 倍）**。两批 `build_id` 与产物大小一致；10 个负载静态指令数和帧槽数不变，四个挂起负载快照大小不变，基准仍校验首次执行、稳态结果及快照续跑。`build_id` 因 `Instr` 标签和二进制字符串/数字表示再次变化；产物格式由 `BUILD_FORMAT_VERSION` 独立约束。

## 复用已验证的构建

`VerifiedBuild::new` 完整校验 `Build` 并派生函数索引和调用元数据。`Vm::new_verified` / `Vm::restore_verified` 共享这个不可变的线程内句柄，不共享堆、缓存或宿主状态。普通入口仍每次校验；复用入口也不省略新 VM 的宿主链接、模块初始化或快照校验。字节码、构建摘要和快照格式不变。

Apple M2 / macOS 27.0.1 / Rust 1.99.1，三批独立 release 进程。每批预热 2 次、采样 11 次；每个样本顺序启动 8 个新 VM、恢复同一镜像 8 次，交错比较普通入口和复用入口。同一二进制和同一产物；每个 VM 使用新宿主，且检查启动后的运行结果或恢复后的续跑。React 在首次提交后捕获，验证提交状态；`await-success` 在宿主等待时捕获，恢复后重挂并完成等待。

```sh
env -u YIELD_VM_BENCH_DIAGNOSTICS cargo bench --locked -p yield-harness --bench baseline -- --verified-reuse --samples 11
```

计时不含编译、产物解码、镜像克隆、宿主重挂和续跑。`verify_once` 单列；下表把它按样本加回每组 8 次的复用总耗时，显示三批中位数的范围。百分比为各批配对变化的中位数范围。[原始 CSV](bytecode-loading/verified-reuse/)。

| 工作负载 | 每次校验，8 次总耗时 | 校验一次 + 复用，8 次总耗时 | 变化 |
| --- | ---: | ---: | ---: |
| React 启动 | 24.50–24.62 ms | 14.65–14.67 ms | −40.3% |
| React 恢复 | 28.85–28.95 ms | 19.23–19.24 ms | −33.5% 至 −33.3% |
| `await-success` 启动 | 2.12–2.15 ms | 2.09–2.11 ms | −2.2% 至 −0.7% |
| `await-success` 恢复 | 3.84–3.87 ms | 3.89–3.92 ms | +0.5% 至 +1.7% |

React 构建约 752 KB，一次校验和派生约 1.42 ms；若调用方已持有句柄，8 次启动和恢复的耗时分别下降约 46% 和 38%。`await-success` 构建只有 2.7 KB，校验约 5–6 µs，恢复仍主要花在堆和快照检查上，未测得恢复收益。此实验不代表单 VM 冷加载收益。

## 二进制快照

`Snapshot::to_bytes` / `from_bytes` 使用 `YIELDSNP`、独立容器版本和镜像记录版本，后接 bincode 小端变长整数编码。JSON 保持原样。二进制和 JSON 解码后走完全相同的恢复校验。

```sh
env -u YIELD_VM_BENCH_DIAGNOSTICS cargo bench --locked -p yield-harness --bench baseline -- --snapshot-codecs --samples 15
```

Apple M2 / macOS 27.0.1 / Rust 1.99.1，三批独立 release 进程；每批预热 2 次，记录 15 个配对样本，交替两格式的运行顺序。对同一捕获记录分别计编码、解码和 `Vm::restore_verified`；已验证构建在计时外共享，捕获、文件 I/O、operation 重挂与续跑也不计时。每次恢复后校验脚本结果。以下时间降幅是各批配对中位数的范围；[原始 CSV](bytecode-loading/snapshot-codecs/)。

| 工作负载 | JSON → 二进制（字节） | 编码降幅 | 解码降幅 | 解码 + 恢复降幅 |
| --- | ---: | ---: | ---: | ---: |
| React 首提交后 | 1,055,295 → 161,557 | 71.2–71.7% | 60.0–60.4% | 30.1–30.6% |
| `await` 成功 | 302,611 → 46,600 | 70.7–70.9% | 57.2–57.7% | 32.8–33.5% |
| `finally` 中 `await` 拒绝 | 303,149 → 46,684 | 70.3–70.9% | 56.8–57.2% | 32.9–33.7% |
| 同步生成器 | 305,015 → 46,940 | 70.2–70.9% | 56.9–57.8% | 33.0–33.4% |
| 异步生成器 | 305,015 → 46,940 | 70.1–71.1% | 57.2–57.5% | 32.9–33.6% |

单独的恢复阶段没有稳定差异，跨负载各批配对中位数变化为 −1.8% 到 +1.4%。React 解码加恢复由 4.51–4.54 ms 降到 3.15–3.18 ms；解码后的恢复自身仍约 2.24 ms。体积和时间收益来自编解码，不来自省略堆还原或校验。
