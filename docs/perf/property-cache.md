# 普通对象属性表与写侧单态缓存

本轮把普通对象的 `PropertyTable` 分成两种存储: 8 个键以内使用按 key 排序的密集向量, 超过 8 个键退回 `BTreeMap`. 小表可以直接给出槽位, 避免 BTreeMap 查找; 大表保持旧布局, 避免 React 这类多属性对象整体变慢.

`SetMember` 增加每站点缓存: 记录接收者身份、键、布局和槽位, 不缓存值或属性描述符. 站点需要先命中 32 次才填入缓存, 因此一次性站点不支付槽查找; 值写入仍走 `set_plain_slot`, 失败时回退完整 `Set` 语义. 读取路径不做站点缓存; 读缓存实验在两批中使 React 首提交的 `entry_first` 回退约 9%, 因此没有启用.

`PropertyTable` 的 JSON 形状保持原样: 字符串键属性仍按有序 pair 序列编码, Symbol 键属性仍按对象编码. 缓存和布局字段不进入快照; 恢复后为空, 快照格式和字节码版本不变.

## 环境与命令

Apple M2 (24 GiB), macOS 27.0.1, rustc/cargo 1.99.1. 基线是提交 `b6aa7d0`; 最终版是同一工作树上的改动. 两版分别跑 A/B 两批, 最终版另跑 C 批, 每批 `--samples 5`, 进程内预热 2 次; 报告使用每批中位数. 复现:

```sh
cargo bench -p yield-harness --bench baseline -- --samples 5
```

原始样本在 [property-cache/](property-cache/): `baseline-a/b.csv`、`write-cache-a/b/c.csv`；读缓存对照样本是 `read-cache-a.csv`.

## 结果

| 负载 / 指标 | 基线 (µs) | 最终版 (µs) | 变化 |
|---|---:|---:|---:|
| React 首提交 / `startup_initialize` | 1520.19 | 1502.92 | −1.1% |
| React 首提交 / `entry_first` | 471.38 | 481.96 | +2.2% |
| React 首提交 / `entry_steady_5` | 2055.79 | 2088.17 | +1.6% |
| React 更新 / `entry_first` | 2605.27 | 2631.58 | +1.0% |
| React 更新 / `entry_steady_5` | 10346.88 | 10324.40 | −0.2% |
| 静态属性 / `entry_first` | 361.79 | 247.42 | −31.6% |
| 静态属性 / `entry_steady_5` | 1708.15 | 1234.08 | −27.8% |
| 短调用 / `entry_steady_5` | 1288.19 | 1262.42 | −2.0% |
| 闭包读写 / `entry_steady_5` | 2068.96 | 2070.54 | +0.1% |

静态属性负载的写站点在热循环中反复更新同一个自有数据属性, 写缓存消除了站点到 BTreeMap/二分查找的路径; 小表排序向量与缓存共同贡献了约 28% 的稳态收益. React 首提交没有同量级的重复写站点, 预热计数和表分支带来约 1–2% 的稳态成本, 但启动准备和更新稳态仍在基线波动内. 四个挂起负载的启动、恢复和稳态没有稳定回退; 样本在 `write-cache-a/b/c.csv` 中.

## 未启用项

- **读侧站点缓存.** 在相同表结构上, 读缓存 + 32 次预热使静态属性仍为 −32%, 但 React 首提交 `entry_first` 从写侧缓存的 475.92 µs 升到 486.08 µs, `entry_steady_5` 从 2093.62 升到 2107.12 µs; 读路径的每次站点检查覆盖不了 React 的一次性读取. 因此只保留写缓存.
- **索引表 + 无预热写入缓存.** 全局索引表把所有键放到 `BTreeMap<K, usize>` + 密集槽向量, 静态属性提升很大, 但 React 首提交稳态回退约 7%; 改成小表向量/大表 BTreeMap 后该回退收窄.
- **读缓存的两态/失配禁用.** 单态、双态和失配禁用变体都在 React 首提交出现回退; 最终只保留写侧的 32 次预热, 避免为了微基准牺牲代表性负载.
