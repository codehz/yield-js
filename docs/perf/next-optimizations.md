# 编译器、VM 与快照：下一轮优化方向

## 已测结果

- [显式 CFG 对照](explicit-cfg.md)：React 离线编译约 90 → 82 ms，峰值 RSS 仍约 38 MiB；更新负载的稳态 5 次分派从 157,425 降到 148,065，未证实同量级的耗时改善。字面量重建实验少保存一个值，只减少 15 B JSON，还多一次续跑分派。
- [加载与恢复对照](bytecode-loading.md)：二进制快照把 React 镜像从 1,055,295 B 降到 161,557 B；后续实验的可信恢复约 0.38–0.40 ms。`VerifiedBuild` 已可复用构建校验与派生表。两项数据来自不同对照，不能相加作为端到端结果。
- 最新 [CFG 计时](explicit-cfg/) 的四个挂起负载，捕获整体中位数约 0.14–0.16 ms。现有挂起镜像主要由堆和宿主状态构成；缺少捕获分项和大 buffer 峰值数据。

## 优先级

1. **快照捕获。** `Vm::snapshot` 先追踪可达图，再构造拥有所有权的对象记录，宿主 payload 与 operation 也在捕获时编码或 checkpoint；之后才调用 `Snapshot::to_bytes`。先独立测追踪、记录构造、宿主工作和二进制编码。负载用 React、挂起脚本和大 `ArrayBuffer` 上的多个 view；后者验证复制的是一份后备存储，而不是每个 view 一份。若记录克隆占主导，再验证借用可达对象直接编码、成功后才发布字节的路径，并测 `capture + encode` 与独立进程峰值 RSS；若追踪占主导，先减少重复堆查询。不改现有格式，验证同状态编码字节、弱引用过滤、buffer/view 别名、宿主出错行为和恢复续跑。
2. **长驻 VM 内存。** 对照无收集、固定间隔、按分配量触发的宿主调度，复用微任务排空后的 `collect_garbage(roots)`。快照追踪不会清扫原 VM。记录长时间堆增长、回收量、RSS 和 p95 暂停；只有暂停成为瓶颈时，再优化标记集合、全表清扫或缓存失效。暂不做解释器内自动或增量 GC。
3. **执行吞吐。** 普通数组数字索引已有快路径，但元素仍在 `BTreeMap`。可验证连续、默认描述符元素走密集存储，稀疏或特殊描述符回退；快照形状不变。测顺序读、覆盖写、`push`、每元素内存和 React；保留空洞原型查找、只读 `length` 和截断语义。历史 [.length 复测](array-access.md#四变体归因复测) 表明新增 opcode 也可能拖慢不执行它的负载。此前通用读缓存和帧缓冲池也未在代表性负载上得到稳定收益。
4. **离线编译。** 先在最新 CFG 上重采样；如果活性集合仍热，单独对照小函数位集与 `BTreeSet`，大而稀疏的函数保留回退。验收离线耗时、RSS 和 `build_id`；保持异常边写入前状态以及恢复边各自扣除注入槽的语义。不为这一步引入 SSA 或通用重建 pass。

首个实验只增加快照分项计时和大 buffer 负载，不改捕获语义或格式。计时与诊断计数分开，比较配对样本；不以指令数、对象数或镜像体积替代耗时和峰值内存。
