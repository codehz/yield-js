# 编译器、VM 与快照：下一轮优化方向

## 已测结果

- [显式 CFG 对照](explicit-cfg.md)：React 离线编译约 90 → 82 ms，峰值 RSS 仍约 38 MiB；更新负载的稳态 5 次分派从 157,425 降到 148,065，未证实同量级的耗时改善。字面量重建实验少保存一个值，只减少 15 B JSON，还多一次续跑分派。
- [加载与恢复对照](bytecode-loading.md)：二进制快照把 React 镜像从 1,055,295 B 降到 161,557 B；后续实验的可信恢复约 0.38–0.40 ms。`VerifiedBuild` 已可复用构建校验与派生表。两项数据来自不同对照，不能相加作为端到端结果。
- 最新 [CFG 计时](explicit-cfg/) 的四个挂起负载，捕获整体中位数约 0.14–0.16 ms。现有挂起镜像主要由堆和宿主状态构成；缺少捕获分项和大 buffer 峰值数据。

## 优先级

1. **快照捕获。** `Vm::snapshot` 先追踪可达图，再构造拥有所有权的对象记录，宿主 payload 与 operation 也在捕获时编码或 checkpoint；之后才调用 `Snapshot::to_bytes`。先独立测追踪、记录构造、宿主工作和二进制编码。负载用 React、挂起脚本和大 `ArrayBuffer` 上的多个 view；后者验证复制的是一份后备存储，而不是每个 view 一份。若记录克隆占主导，再验证借用可达对象直接编码、成功后才发布字节的路径，并测 `capture + encode` 与独立进程峰值 RSS；若追踪占主导，先减少重复堆查询。不改现有格式，验证同状态编码字节、弱引用过滤、buffer/view 别名、宿主出错行为和恢复续跑。
2. **长驻 VM 内存。** 对照无收集、固定间隔、按分配量触发的宿主调度，复用微任务排空后的 `collect_garbage(roots)`。快照追踪不会清扫原 VM。记录长时间堆增长、回收量、RSS 和 p95 暂停；只有暂停成为瓶颈时，再优化标记集合、全表清扫或缓存失效。暂不做解释器内自动或增量 GC。
3. **执行吞吐。** 普通数组数字索引已有快路径，但元素仍在 `BTreeMap`。可验证连续、默认描述符元素走密集存储，稀疏或特殊描述符回退；快照形状不变。测顺序读、覆盖写、`push`、每元素内存和 React；保留空洞原型查找、只读 `length` 和截断语义。历史 [.length 复测](array-access.md#四变体归因复测) 表明新增 opcode 也可能拖慢不执行它的负载。此前通用读缓存和帧缓冲池也未在代表性负载上得到稳定收益。
4. **离线编译。** 先在最新 CFG 上重采样；如果活性集合仍热，单独对照小函数位集与 `BTreeSet`，大而稀疏的函数保留回退。验收离线耗时、RSS 和 `build_id`；保持异常边写入前状态以及恢复边各自扣除注入槽的语义。不为这一步引入 SSA 或通用重建 pass。

首个实验只增加快照分项计时和大 buffer 负载，不改捕获语义或格式。计时与诊断计数分开，比较配对样本；不以指令数、对象数或镜像体积替代耗时和峰值内存。

## 快照捕获分项实测

```sh
env -u YIELD_VM_BENCH_DIAGNOSTICS cargo bench --locked -p yield-harness --bench baseline -- --capture-profile --samples 15
```

Apple M2 / macOS 27.0.1 / Rust 1.99.1。两批独立 release 进程，每批预热 2 次、采样 15 对。对同一暂停状态交替执行普通与分项捕获；每对要求二进制字节一致，两份镜像都解码、恢复并验证续跑。三段之和逐样本等于分项捕获总时间。`capture_host_records` 含宿主记录构造、payload codec 和 operation checkpoint，不是纯回调时间。`binary_encode` 只计普通捕获所得记录的二进制编码；构建、初始化、解码、恢复、重挂、续跑、文件 I/O 和记录析构不计入表中。原始数据：[A](snapshot-capture/a.csv)、[B](snapshot-capture/b.csv)。

- **对象图多、二进制内容少：** React 捕获约四分之三在追踪，小挂起负载约三分之二；若以这些负载为主，先验证减少标签与边遍历中的重复堆查询，而不是先做借用式编码。
- **后备存储大：** 夹具让一个 8 MiB buffer 跨 `await` 存活，`Uint8Array` 和尾部 `DataView` 共享该 buffer。续跑检查身份、首尾字节，并通过一个 view 写、另一个读；最终镜像 8,435,155 B、518 个对象。VM 记录构造超过追踪，但二进制编码约占捕获加编码的九成；若目标是延迟，先检查大字节块的编码吞吐。若目标是峰值内存，再验证绕过中间镜像的收益；本轮没有测峰值 RSS。大 buffer 的配对差异受顺序和样本波动影响，不用来推断计时探针成本。
- 宿主记录在这些夹具中都不足 1 µs，不外推到自定义 checkpoint 或大 payload。捕获与快照格式均未优化或改版，本轮只建立分项基线。

### 大 buffer 批量编码复测

`ArrayBuffer` 的非文本编码改用 Serde `serialize_bytes`。Bincode 仍写相同的 `Option` 标记、变长长度和原始字节，改为一次批量写入，而非逐 `u8` 写入；JSON、解码与快照版本不变。用优化前后两个编码器互相解码并重编码，对 8 MiB 挂起镜像以及包含已分离、空、251 字节 buffer 的镜像逐字节比对，结果一致。

对照为 `eaa1f52`，候选只改 buffer 序列化。复用上面的命令和环境，两批分别按「对照 → 候选」「候选 → 对照」顺序各跑 15 对样本。数据：[对照 A](snapshot-capture/bulk-control-a.csv)、[候选 A](snapshot-capture/bulk-candidate-a.csv)、[对照 B](snapshot-capture/bulk-control-b.csv)、[候选 B](snapshot-capture/bulk-candidate-b.csv)。

| 8 MiB `ArrayBuffer`，中位数 | A：对照 → 候选 | B：对照 → 候选 |
| --- | ---: | ---: |
| 二进制编码 | 4.135 → 0.762 ms | 4.172 → 0.780 ms |
| 捕获 + 二进制编码 | 4.528 → 1.146 ms | 4.560 → 1.223 ms |

大 buffer 编码时间下降 81–82%，捕获加编码下降 73–75%，镜像仍为 8,435,155 B。React 与小挂起负载跨批波动明显，不据此宣称提速。未改捕获复制或解码，也未测峰值 RSS。

### 复用追踪对象引用

追踪首次发现对象 ID 时查一次堆对象主表，将 ID 和对象引用一并入队。重复边只查活集；展开时用已取得的对象枚举边，WeakMap 的定点迭代也复用条目表引用。首次查找仍拒绝缺失 ID，生成器、组合 Promise 和私有元素的侧表仍由 `Heap::write_edges` 处理。GC 共用该追踪路径；快照的记录克隆与排序不变。
