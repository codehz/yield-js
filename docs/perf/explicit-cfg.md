# 显式 CFG：架构评估与优化计划

架构评估基于 `f5773fa`；本轮性能对照取已完成普通跳转清理的 `9bc6b31`，不使用历史报告中的数据。当前契约见[内部契约](../internals.md)。

## 架构评估

- 保留可变逻辑寄存器 CFG。异常与挂起恢复已经进入数据流；现阶段的优化不依赖 SSA。
- 降低仍发射线性指令、回填 PC，再由 `FunctionCfg::from_lowered` 解码为块；布局仍把普通分支的一侧视为相邻块。先约束 CFG 变换，再逐步把普通分支和布局解耦。不一次性重写 lowerer。生成器首次入口、`yield` 的 `next` 相邻性及 `throw` / `return` 入口独占性由现有 VM 契约约束，不随普通块重排改变。
- 保存集合只依赖恢复目标的块入口活性：每条边先减去自身注入槽再取并集；生成器首次进入取完整活性。布局直接从块入口活性取保存集合，按最终 PC 流式累积瞬时槽区间，不物化逐 PC 活性表。
- CFG 当前保守地给可抛点添加所有覆盖 handler，VM 只选择优先级最高的一个。后续可单独提高精度；异常传递仍使用指令写入前的状态，不能与挂起拒绝边混用。

## 实施结果

1. **CFG 校验与普通跳转清理**（`9bc6b31`）：校验入口、目标与异常保护；清理普通跳板和相邻直跳，保留可能转换或抛错的同目标测试以及特殊入口。保持源块顺序和现有字节码编码。
2. **折叠和指令选择**（`6c94022`）：折叠可证明的原始值严格比较和少量 Number 运算；已知、可入池的右操作数选用 `BinaryConst` 或常量比较分支，不交换操作数。数据流仍在合流点取交集，不把不同的 `finally` 完成种类合并成常量。
3. **挂起后重建字面量**：完成下文的成对实验；收益仅为单个保存值和少量快照字节，未引入通用重建。
4. **编译成本及槽分配**（`4665fdc`）：按前驱重访活性受影响的块，覆盖普通、异常和恢复边；布局直接累积 PC 区间。未改变瞬时槽区间模型或持久槽不复用规则。未改用密集集合或批量声明分析，也未拆分槽区间。

## 验证与度量

- 工作区 716 项测试通过，覆盖普通跳板、转换副作用、异常保护、`await` 拒绝、挂起的 `finally` 与生成器的 `next` / `throw` / `return`。
- 复用[基准入口](performance-baseline.md)。三组对照：`control` 为 `9bc6b31`，`alloc` 只应用 `4665fdc` 的 `crates/compiler/src/` 差异，`candidate` 同时应用折叠和分配改动。各组在同一台 Apple M2、macOS 27.0.1、Rust 1.99.1 上构建；A 批按 `control → alloc → candidate` 运行，B 批逆序。每组预热 2 次、取 9 个样本，诊断计数单独运行。`--compile-only` 以 `/usr/bin/time -l` 对每个负载单独采集三次峰值 RSS。
- 各产物使用自己的 `Build` 验证快照往返与续跑结果，不交叉恢复。字节码、产物容器与快照格式均不变；重新编译仍可能改变 `build_id`。仅改分配的对照与基线所有基准负载的 `build_id` 相同。

## 本轮实测

原始数据见[计时、诊断计数和峰值 RSS](explicit-cfg/)。静态指标与分派数比较 `control → candidate`；动态分派为稳态 5 次总计。

| 负载 | 静态指令数 | 稳态分派数 |
| --- | ---: | ---: |
| React 首提交 | 32,068 → 30,964 | 24,740 → 23,710 |
| React 更新 | 32,068 → 30,964 | 157,425 → 148,065 |
| 数值/分支 | 43 → 43 | 186,920 → 186,920 |

React 二进制产物由 749,127 B 减到 702,114 B。四个挂起负载的续跑结果一致：

| 负载 | 初次挂起保存值数 | JSON 快照字节 | 首次续跑分派 |
| --- | ---: | ---: | ---: |
| `await` 成功 | 0 → 0 | 302,611 → 302,611 | 516 → 516 |
| `finally` 中 `await` 拒绝 | 2 → 1 | 303,149 → 303,134 | 7 → 7 |
| 同步生成器 | 1 → 1 | 305,015 → 305,015 | 99 → 97 |
| 异步生成器 | 3 → 3 | 305,015 → 305,015 | 108 → 106 |

用 `sample` 对基线的 React 编译采样，活性求解、逐 PC 活性生成与槽分配均出现在热点栈上。下表是 React 首提交产物的离线编译中位数，RSS 为三次独立进程的峰值中位数。

| 对照 | 编译 A / B（ms） | 峰值 RSS（MiB） |
| --- | ---: | ---: |
| `control` | 90.62 / 89.87 | 38.00 |
| `alloc` | 81.48 / 81.71 | 37.84 |
| `candidate` | 81.93 / 81.94 | 38.05 |

单独改活性与分配使 React 离线编译缩短约 9–10%，合并后仍缩短约 9–10%。进程峰值 RSS 未见明确下降；不从省去逐 PC 表推断峰值内存收益。React 稳态、数值/分支及恢复计时不据此宣称提速。

## 字面量重建实验

用同一个 Build 对照 `13 + (await wait(...))` 与先 `await` 再加载 `13`，模拟把已证明不变的 Number 字面量移到恢复侧。不改变优化器；两条路径分别捕获、JSON 往返并恢复，均得到 `20`。

| 路径 | 初次挂起保存值数 | JSON 快照字节 | 恢复后首次续跑分派 |
| --- | ---: | ---: | ---: |
| 挂起前加载 | 1 | 302,584 | 2 |
| 恢复后加载 | 0 | 302,569 | 3 |

少保存一个值只减少 15 B，代价是恢复侧多一次分派。常规挂起负载的镜像主要由堆和宿主状态构成；本轮不引入通用重建 pass，也不把这个微基准解释为恢复提速。复现时给 `baseline` 基准加 `--rematerialization`，计时与 `YIELD_VM_BENCH_DIAGNOSTICS=1` 计数分开执行。
